Bug found in run_rep_stage3_0_four_eight.sh while investigating the kill's
aftermath: the master log's own summary ("Failed experiments: N", "✓ All
experiments completed successfully!") is structurally unreliable. Each
experiment's per-step subshell is `( ... ; if python -m ...; then echo ✓...;
else echo ✗...; fi; echo "End time: ..." ) &` -- since the subshell's LAST
command is always the unconditional `echo "End time..."` (which always
succeeds), the subshell's own exit code is always 0 regardless of whether
the inner python command failed. The outer wait-loop's `wait
"${exp_pids[$experiment]}"` waits on that subshell PID, not the python
PID, so it always sees success and the master log always reports 0
failures -- confirmed here: master log shows "✓ dynamic_deephit completed
successfully" and "Failed experiments: 0" even though dynamic_deephit's OWN
log clearly shows "✗ dynamic_deephit failed with exit code 143". This also
explains an earlier-noticed quirk (cox/logistic_hazard/rnnsurv's
completions were absent from the master log's own "✓ ... completed
successfully" lines during this same run, even though they'd genuinely
finished) -- the master log's line only appears when the *subshell*
happens to still be tracked/waited correctly, but its truth value (✓ vs ✗)
can't be trusted either way. The individual per-experiment logs
(pkgs/scripts/eval_rep1_stage3_0_four_eight_<experiment>.log) are the only
reliable source of pass/fail status for this script -- not fixed here (out
of scope for this session's task), flagging for whoever next touches
run_rep_stage3_0_four_eight.sh / the shared run_rep.sh pattern it mirrors.
