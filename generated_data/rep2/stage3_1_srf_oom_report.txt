Stage 3.1 — rep2 `srf` OOM-kill incident (sunlab-serv-02.cs.illinois.edu)
==========================================================================

What happened
--------------
During the 2026-08-29 19:17-19:26 CDT auto-check window, rep2's `srf`
subprocess (part of the `pkgs/scripts/run_rep.sh 2` background run, PID
531632) was killed by the kernel OOM killer:

  eval_rep2_srf.log:
    ✗ srf failed with exit code 137
    End time: Sat Aug 29 19:26:15 CDT 2026

  dmesg -T:
    [Sat Aug 29 19:22:33 2026] tcp invoked oom-killer: ...
    Out of memory: Killed process 531711 (python) total-vm:60456452kB,
    anon-rss:52801236kB, ...

531711 is a child of rep2's srf invocation (`python -m pkgs.experiments.srf`,
PPID 531670 per the process tree). This is a genuine host-memory OOM kill,
not a code exception — exit 137 = 128+SIGKILL.

Root cause
----------
`pkgs/experiments/srf.py`'s `run_survival_rf()` / `run_scenario()` both run
`GridSearchCV` over `RandomSurvivalForest(n_jobs=2)` with
`param_grid = {'n_estimators': [50,100,150], 'max_depth': [None,5,10],
'min_samples_split': [2,5,10,15]}` — the `max_depth=None` (unbounded trees)
combos at higher `n_estimators` are memory-heavy: a single such fit was
observed to peak at ~45-53GB RSS in isolation (confirmed by watching rep3's
still-running `srf` process cycle between ~3GB baseline and ~53GB peak per
GridSearchCV fold/combo, dropping back down each time a fit completes).

The crash was a **collision**, not a leak: rep2 and rep3 were launched
concurrently on the same host (sunlab-serv-02, 188GB RAM + 8GB swap) per
Stage 3.1, each running all 11 experiments in parallel — including their own
`srf` process. When rep2's and rep3's `srf` GridSearchCV fits both happened
to hit a `max_depth=None`/high-`n_estimators` combo at the same moment
(~2x50GB), combined with the other 9 experiments per rep already running
concurrently (cox/hazard_transformer/rnnsurv/logistic_hazard/deepsurv/
dynamic_deephit — ~90GB baseline observed), swap (8GB) filled and the OOM
killer picked rep2's `srf` child.

This is consistent with prior unrelated OOM kills logged in `dmesg` from
other sessions/dates (2026-08-23, 2026-08-27, 2026-08-29 05:57) — `srf`'s
GridSearchCV grid is inherently memory-heavy even running alone; running two
full reps' `srf` concurrently on one host measurably increases collision risk
but is not required to trigger it.

No other rep2 experiment was affected — the parent `run_rep.sh 2` process
(PID 531632) and its other 10 experiment subprocesses continued running
unaffected; only the `srf` child died.

Mitigation applied
-------------------
Not a code bug to fix in `srf.py` (the grid/config is existing, approved
model code) — this is a scheduling/resource-contention issue. Chosen fix:
**do not relaunch rep2's `srf` while rep3's `srf` is still mid-GridSearchCV**
(avoid a repeat simultaneous-peak collision); relaunch rep2's `srf` alone,
standalone (`CKD_REP=2 python -m pkgs.experiments.srf`, not the full
`run_rep.sh 2`, since the other 10 rep2 experiments are already running/some
already done and must not be restarted) once rep3's `srf` has finished or
memory headroom is otherwise confirmed safe. Tracked for the next 10-minute
auto-check cycle.

No model artifacts were lost: `generated_data/rep2/` has no partially-written
`*srf*` model file, so the relaunch redoes `run_survival_rf()` +
`FOUR_FEATURES`/`EIGHT_FEATURES`/`TWENTY_FEATURES_HETEROGENEOUS` from
scratch for rep2 — no partial-progress caching to preserve here.

Open consideration for the user (not acted on autonomously): if `srf`
OOM-collisions recur across reps, consider either (a) capping `srf` to
`n_jobs=1` / adding a max_depth cap to the grid to shrink peak RSS, or
(b) never launching more than one rep's `srf` at a time on a shared host.
Flagged, not applied — changing the model's hyperparameter grid affects
results and needs sign-off per CLAUDE.md's model-change rules.

Update 2026-08-29 19:48 CDT — rep3's `srf` ALSO OOM-killed
-------------------------------------------------------------
rep3's `srf` (PID 532843) died the same way ~22 minutes *after* rep2's `srf`
was already dead — ruling out simultaneous cross-rep collision as the sole
cause:

  dmesg: python invoked oom-killer ... Killed process 532843 (python)
  total-vm:99845696kB, anon-rss:92466860kB ...

anon-rss at kill time was ~92GB — nearly double the ~45-53GB peaks observed
earlier per-fit. Neither rep2's nor rep3's `srf` ever got far enough to save
a single model artifact (`generated_data/rep{2,3}/` has no `*srf*` files at
all) despite ~48-55 minutes of runtime each and 10+ completed GridSearchCV
fit blocks — meaning `run_survival_rf()`'s very first `grid_search.fit()`
call (36 param combos x 5-fold CV, up to 180 individual RandomSurvivalForest
fits) hasn't completed even once before crashing, and a retry restarts that
entire unbounded grid search from scratch (no checkpointing exists).

Revised assessment: this is not purely a two-reps-on-one-host scheduling
collision — a solo `srf` GridSearchCV run, on top of the other 9
experiments per rep already resident (~94GB baseline observed across rep2's
+ rep3's remaining processes), can by itself grow to ~90GB+ RSS on later
(likely `max_depth=None`, higher `min_samples_split`/`n_estimators`) param
combos and exhaust the host. Blindly relaunching a 3rd time risks a 3rd
~50-minute wasted run.

**Decision: holding both rep2 and rep3 `srf` retries** rather than
relaunching again immediately. This needs either (a) user sign-off on
capping the grid (e.g. drop `max_depth=None`, cap `n_estimators`) to shrink
peak RSS — a results-affecting model change per CLAUDE.md's rules — or (b)
waiting until enough of the other 6-7 still-running experiments per rep
finish to free real headroom before retrying the existing grid as-is. Not
acted on autonomously; flagged to the user. The rest of rep2 (6 experiments)
and rep3 (7 experiments) continue unaffected in the meantime.

Update 2026-08-30 17:41 CDT -- duplicate concurrent launches detected and cleaned up
----------------------------------------------------------------------------------------
Found THREE separate `python -m pkgs.experiments.srf` processes alive
simultaneously for rep2 (CKD_REP=2), all writing to the SAME log file
(pkgs/scripts/eval_rep2_srf.log): PID 763722 (started 17:08), PID 764996
(started 17:20, died on its own by 17:35 -- unclear if OOM'd or killed by
whatever spawned the next one), and PID 768035 (started 17:35, just
starting up). This is evidence of multiple concurrent sessions/agents each
independently deciding to retry rep2's srf without checking for an
already-running attempt first -- likely following the user's "always auto
retry" instruction literally on each check, in parallel, without
coordinating.

This is actively harmful, not just wasteful: concurrent processes writing
to the same log file interleave/corrupt their output, and -- more
seriously -- they'd all eventually try to write the SAME model artifact
paths (four_features_srf_model.dill etc.) once/if any of them completes a
GridSearchCV fit, risking a corrupted or silently-wrong saved model if two
writes race.

Action taken: killed the newest duplicate (PID 768035, just started, zero
progress) via SIGTERM. Left PID 763722 running (started 17:08, most
progress, ~19min in with several completed GridSearchCV fit blocks) as the
sole rep2 srf process. Did not touch anything on rep3's side.

**If you are another session reading this**: before launching another rep2
srf retry, run `ps aux | grep experiments.srf` first and check whether
PID 763722 (or its eventual successor, whichever this repo's
EXPERIMENT_STATUS.md rep2 row currently names) is already running -- don't
launch a second one on top of it.
